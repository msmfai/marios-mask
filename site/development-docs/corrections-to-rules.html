Turning corrections into rules

Purpose: make sure that the same correction is not needed twice.

Summary

A correction in a conversation is lost when the conversation ends. The next agent makes the same mistake. Thus a correction is complete only when it exists in a form that every later session sees or that runs automatically.

The rule on this project: a correction is not complete until it is a test, a reference capture, a save state with a script, a runtime assertion or a checklist.

Procedure

  1. Reproduce the fault that the owner reported. If an earlier fix failed, revert it first.
  2. Check whether the behavior is a deliberate design choice. If it is, ask the owner, and record the exception so that later audits do not change it.
  3. Write the lesson: what happened, why, and how to apply the rule.
  4. If the rule can be checked by a program, write a gate or test.
  5. Run the new gate on the code before the fix. It must fail. If it passes, the gate is wrong. Repair it and run it again.
  6. Add the gate to the suite that runs for that kind of change.

Proving a new gate

  • A gate that never failed proves nothing. Run it on a baseline built from the code before the fix.
  • One gate passed the exact output that it was written to reject. The generator split commands across lines, and the gate read one line at a time.
  • One gate fix was proven by a deliberate fault in one actor. The gate gave the expected error.
  • If a fix is reverted because it was a theory, revert the checks that were based on that theory too.
  • A gate can also be wrong. Then fix the gate table and record the values before and after, so that the change does not look like a weaker gate.
