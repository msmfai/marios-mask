Directing agents

Purpose: give the method to write a task that an agent can do without supervision, and to stop it when it goes wrong.

Summary

Agents do good work when the task is small, the result can be tested, and the limits are written down. Most of the losses on this project came from four causes:

  • Agents changed files before the scope was agreed.
  • Several agents worked at once on shared things.
  • Project state was kept in very long conversations.
  • Progress was measured by agent activity, not by accepted results.

The method in this document removes these causes. It comes from a review of one month of agent sessions (July 2026: 2,108 owner prompts, 71 sessions, 22 active days).

Procedure

  1. Write a task contract (see below).
  2. Set the authority mode. If the mode is not stated, the agent only inspects.
  3. Assign one agent. Use more agents only under the conditions in document 9.
  4. The agent does one slice.
  5. If a stop rule applies, the agent returns to the last accepted state and keeps the evidence.
  6. If no stop rule applies, the agent writes a checkpoint. The checkpoint ends with one decision: continue, accept, rescope or roll back.
  7. When the work is accepted, the agent writes a handoff. The next task starts in a new conversation.

Task contract

FieldContent
ModeOne authority mode (see below)
OutcomeOne behavior that a person can see or a test can measure
EvidenceThe test, capture or measurement that shows the outcome
Non-goalsRelated work that the agent must not do
Allowed changesThe files, branches and systems that the agent can change
InvariantsConditions that must stay true, for example memory limits
CheckpointWhen the agent stops and reports
Stop and rollbackThe condition that ends the attempt, and the state to return to

Authority modes

ModeThe agent can
InspectRead and run read-only commands. This is the default.
ProposeWrite a plan. Change no files.
ImplementChange files inside the allowed scope. This is the default in a feature worktree.
ReviewRead and report. A reviewer does not repair what it finds.
IntegrateMerge accepted commits
ReleaseRun the release tooling. Only on the owner's request.

Slices

Divide large work into vertical slices. A slice:

  • makes one behavior that can be seen or measured;
  • can be tested alone;
  • has one owner and one rollback point;
  • leaves the repository usable if the later slices are cancelled.

One 4-day migration on this project had no slices. It was declared a failure at the end.

Checkpoints and handoffs

A checkpoint records the completed work, the evidence, the changed files, the invariants that were checked, and the assumptions that were not checked.

A handoff records the exact commit, the authority mode, the acceptance evidence, the known failures, the processes that still run, the next slice and the rollback point.

Project state goes into commit-linked documents. Conversations are temporary. One session on this project ran for about 12 days and 918 prompts, which was 44% of all prompts in the month. Long conversations lose accuracy, so start a new one at each accepted milestone.

Stop rules

The agent stops and reports when one of these occurs:

  • It cannot state the acceptance test.
  • The owner corrects the same requirement twice.
  • Two status checks pass with no new validated result.
  • The rollback point is unknown.
  • A fix did not work. Revert the fix before the next attempt. Do not put a second fix on top of a failed one.

Agent instructions

Each repository has instruction files that the agent reads at the start of each session. They contain:

  • what the product is, and what it is not;
  • the architecture rules (document 6);
  • the supported build and test commands;
  • which tests to run during development, and which only for a release;
  • safety rules, for example limits on file searches outside the repository;
  • how to start the emulator.

Each new agent session starts with a generated prompt. The prompt names the exact branch and worktree, and the agent must check them. The agent then sets a persistent goal before it investigates.

Long-running work

  • Some builds and test gates take many minutes. The agent gives them to a background shell or a sub-agent and continues other work. It does not wait.
  • The owner removed slow exhaustive gates from ordinary development. For example, the boot test of all areas took 15 to 25 minutes and now runs only on request.
  • Before the agent reports a finding, it runs the same measurement on a healthy build (document 11).
