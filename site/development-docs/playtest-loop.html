Owner playtest loop

Purpose: describe how manual play produces evidence that an agent can use without the owner present.

Summary

The owner tests the game by playing it. Manual play finds faults that automated tests do not find: wrong feel, wrong presentation, and faults in places no test visits.

A note such as "the platform is broken" is not enough for an agent. The agent was not present and cannot see the screen. Thus each report records the full game state at the moment of the fault. The agent can load that state and see the fault itself.

Procedure

  1. The owner plays the ROM in the ares emulator through a playtest harness.
  2. When the owner sees a fault, they push one button: a key on the keyboard or the View button on an Xbox controller.
  3. The emulator saves a screenshot and a full save state at the same time.
  4. The harness pauses the game and asks for a one-line note. The game does not advance, so the state matches the screenshot.
  5. The harness reads the game context from RAM with the ROM symbol map and adds it to the report.
  6. The report goes into one queue. All worktrees share this queue. An HTML gallery shows the reports, newest first.
  7. An agent lists the open reports, reads one, and loads the saved state in the emulator.
  8. The agent fixes the fault, commits, and sets the status to "fixed". It can record the fixing commit.
  9. The owner replays the case. If the fault is gone, the owner sets the status to "verified". If not, the report goes back to the agent (not shown in the figure).

Automatic freeze reports

A freeze can stop the owner from pressing a button. Thus the harness also watches the game:

  • About once per second, the harness checks that new frames appear.
  • After 8 seconds with no new frame, it halts the CPU. It files a report with the CPU registers, the faulted thread and a full 8 MiB RAM dump.
  • If the video interrupts also stop, the emulator is paused, not frozen. The harness files nothing.

Report content

ItemContent
ScreenshotThe frame at the button press
Save stateThe full emulator state. It loads only in the same ROM.
Flash saveThe in-game save at capture time
Build identityBranch, commit, a flag for uncommitted changes, and the ROM SHA-256
Game contextScene, room, player position and facing, form, masks, state flags, day and time. This needs the ROM symbol map. Without it, the report has only the screenshot, state and save.
NoteThe owner's one-line description
RAM dump (freeze only)8 MiB RDRAM and CPU registers

Statuses

StatusMeaningSet by
newFiled, not readHarness
investigatingAn agent works on itAgent
fixedA commit claims to fix itAgent
verifiedThe owner replayed it and the fault is goneOwner
wontfixThe behavior stays, by decisionOwner
duplicateAnother report covers itAgent

"new", "investigating" and "fixed" count as open. An agent can set "fixed", but only the owner can set "verified". The person who saw the fault confirms that it is gone.

History and current state

  • The harness was added on 2026-10-16. Before that, the owner reported faults as notes in GitLab work items. A playtest report in September 2026 started the parallel work wave described in document 9.
  • On 2026-11-12 the queue held 1 report, with status "new". No report had reached "fixed" or "verified" yet. The loop is new, so this document describes the design more than a measured record.

Rules

  • Do not ask the owner to describe a fault again. Load the saved state.
  • Check the build identity first. A save state from another ROM shows a different game.
  • An agent does not close its own fix. The owner verifies it.
  • Use the emulator that shows the fault. Some graphics hangs occur in ares and on real hardware, but not in other emulators (see document 11).
