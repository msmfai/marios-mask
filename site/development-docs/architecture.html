Architecture for agent work

Purpose: describe the architecture rules that limit what an agent change can break.

Summary

An agent change can break more than it touches. The architecture limits this. Majora's Mask (MM) is the engine. The imported Super Mario 64 (SM64) code is one transformation form inside it, with one narrow connection. Every build starts again from a clean, pinned copy of the MM decompilation. Audits check the linked ROM, not the source.

Ownership

MM owns these systems: the frame loop, scenes, the Player, input, collision, camera, actors, rendering, audio, messages, save data, the clock and memory.

The imported Mario code has none of these. It has no world, object loop, surface pool, camera, sound mixer, save data or frame output of its own.

  • Mario is a Player form. The normal Player lifecycle creates and removes him.
  • The Mario code reads MM state through one adapter. It advances one movement step and returns the result. The adapter makes the result agree with doors, carried objects and cutscenes, and then writes it to the MM Player.
  • MM enemies keep their own AI, damage, drops and switches. Mario behavior connects at the smallest MM point that works. A broad replacement loop is an architecture fault.

Thus an agent that changes Mario cannot change how an enemy works, and an agent that changes an enemy cannot change Mario's physics.

Build

  1. The build uses a pinned commit of the MM decompilation. It is never edited by hand.
  2. Assets are extracted from the player's own ROMs on the local machine.
  3. The build applies an ordered series of patches to the MM copy.
  4. The build links the ROM.
  5. The invariant audit and the residency checks read the linked ROM.
  6. The build restores the MM copy. This also occurs when the build fails.

Invariant audit

A mandatory audit reads the linked ROM. It checks:

  • the executable format and the ROM header;
  • the DMA table: limits, order, alignment and the end marker;
  • the segment layout;
  • that model, animation, dialogue and emblem data stay in ROM and are not loaded permanently.

The invariants document lists 12 enforced contracts. Each contract also states what it does not prove. Real N64 hardware is the final gate.

Patch stack hygiene

A patch shows the intent at the time it was written. Later patches can change the same code. Thus old patch comments can be wrong. An audit finds patches that later patches overwrite, and comments that the current source contradicts. It never deletes or changes a patch. Reviewed findings are marked in a data file. A check fails on any new unmarked finding.

The September 2026 report found 211 active patches: 38 partly overwritten, 8 candidates for full replacement and 86 contradicted comments.

Memory rule

ROM space is large. RAM is 8 MiB and is almost full.

  • Data that the game does not change stays uncompressed in ROM.
  • The game loads only the data that the current form, actor or scene needs.
  • Data stays in memory only for as long as its user exists.

An agent once linked about 227 KB of imported data permanently. MM outdoor scenes then ran out of memory. A residency check now fails when permanently linked data has no second user.
