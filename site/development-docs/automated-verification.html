Mario's Mask builder

Automated verification of Mario's Mask

Technical reference. Date: 2026-11-09.

Executive summary

Product. Mario's Mask is a mod of the Nintendo 64 game The Legend of Zelda: Majora's Mask (MM). It adds Mario as a playable form. Mario uses the movement code of Super Mario 64 (SM64). The mod also imports SM64 levels and enemies into MM.

Problem. The two games use different units, different update rates and different memory layouts. An error at one of these boundaries can make Mario move incorrectly, make a level look wrong, or stop the game. Many of these errors do not show in an emulator, or show only in one area out of many.

Method. The test system uses the original SM64 game as the reference for correct behavior. It does not use a description of SM64. The test system has six layers:

  1. Static gates check the source and the data on each build.
  2. Headless emulator runs play recorded inputs. Test code in the ROM writes results to memory, and the test reads them through a debugger.
  3. A comparison runs SM64 and the mod side by side and compares Mario tick by tick.
  4. An area sweep loads all 45 imported SM64 areas and records an image of each.
  5. The owner plays the game to answer specific questions only.
  6. A real N64 gives the final check before release.

Tools. The emulator is ares v148 at a pinned version, in three builds: stock (normal tests), 32 MiB (long logs) and capture (records each memory write).

Rules. Ten rules control all tests (section 5). The most important rules are these:

  • A result is valid only if the game itself shows it.
  • A gate is valid only if it fails on the code before the fix.
  • A measurement is valid only after a control on a good build.

2 Background

2.1 Architecture

MM controls the game. MM owns the game loop, the scenes, the actors, the collision, the camera, the memory and the save data. The SM64 movement code runs inside the MM player as one more player form. It reads MM state through small adapters. It writes its result back to the MM player.

The SM64 levels and enemies are generated from the SM64 source on each build. They use MM methods to load and draw.

2.2 Risks

The test system exists to find the faults in Table 2. Each risk comes from a difference between the two games.

Table 2 Main risks

RiskCauseExample of a fault
UnitsOne MM unit is 3.432 SM64 units. Only lengths must use this factor.An enemy model with its parts 3.432 times too far apart.
TimeSM64 updates 30 times each second. MM updates 20 times.Mario moves through a wall after the speed conversion.
MemoryThe N64 has 8 MiB of RAM. MM uses most of it.A level does not load because the object data is too large.
GraphicsA bad display list stops the N64 graphics processor. Some emulators ignore it.A freeze that occurs on hardware but not in the emulator.
ScaleThere are 45 SM64 areas. Manual play cannot examine all of them.A fault class in 18 areas that no player saw.

2.3 Definition of correct behavior

The mod is correct when these three conditions are true:

  1. Mario moves as in SM64. Only the written conversions for units and time are different.
  2. MM systems continue to operate as in MM. These include actors, damage, switches, cutscenes and saves.
  3. The game operates on a real N64 in the available memory. It does not freeze or crash.

Sections 7 to 9 test these conditions. Section 10 finds the cause when a test fails.

5 Verification rules

Purpose: This section gives the rules that all procedures must obey.

These rules apply to all procedures in this document. The procedures refer to them by number. Each rule comes from a known incorrect result.

RuleRequirementReason
R1Use the original game as the oracle.A description of SM64 is not a reference. The SM64 ROM gives repeatable values.
R2Write down each conversion. Check the relation, not a fixed number.The scale changed from 4.29 to 3.432. Gates with fixed numbers then failed on correct code.
R3Check each part of a conversion: vertices, scale, part offsets and animation root.The penguin scale was correct, but its parts were 3.432 times too far apart. The same fault was in 26 actor overlays.
R4Make sure that a gate fails on the code before the fix.A lighting gate passed the fault that it was written for. The generator split one command across two lines.
R5Do a control before you make a conclusion.Several freeze measurements gave the same value on a good build.
R6Do not measure a ROM that is older than its source.A capture command did not build the ROM. It reported the previous build.
R7When a gate rejects correct source, examine the gate.A budget gate charged each actor for the children of one spawner. It reported 58 of 45. The correct count was 27.
R8Use only results that the game shows.Input playback on the host can succeed when the game gets no input.
R9Look at the image.A size ratio cannot show the difference between a small model and a model in pieces.
R10Ask for manual play only for one specific question. Test on a real N64 before release.Emulator results do not replace the hardware test.

6 Emulator builds

Purpose: This section describes the three emulator builds and when to use each build.

All emulator builds start from ares v148, commit 0aafd857. The version is pinned. It does not update automatically. Figure 1 shows the three builds. Table 3 compares them.

Table 3 Emulator builds

StockNone. Each run uses a signed copy with an input bridge.All normal headless tests—

6.1 Stock build

The stock build is the official signed ares v148 application. A run tool starts each run. For each run, the tool does these steps:

  1. It makes a private run folder with its own settings, saves, screenshots and log.
  2. It copies the settings from a fixed base profile.
  3. It copies only the ares executable into the run folder.
  4. It compiles an input bridge into the copy. Stock ares on macOS ignores synthetic key events. The bridge supplies the script inputs.
  5. It signs the copy with an ad-hoc signature. The installed application does not change.
  6. It writes a run record. The record contains the ROM hash, the ares hash, the arguments, the input profile, the save source and the exit status.

Table 4 Headless run settings

SettingValueReason
VideoNoneNo window is necessary.
AudioOn, mutedThe audio driver sets the real-time frame clock.
Rewind, run-aheadOffThe emulator must not replay frames.
Homebrew modeOn (default)Gives debug access.
GDB serverPort 9123Memory reads and breakpoints.
Save formats.flash (131,072 bytes), .srm (296,960 bytes)The tool converts the save in the run folder only.

6.2 32 MiB diagnostic build

A build script applies a source patch to the pinned ares source. The script stops if the source has other changes.

The patch gives the emulator 32 MiB of RDRAM. The game sees only the low 16 MiB. Only the CPU and the debugger can read the upper 16 MiB. The RDP and VI use 24-bit addresses, so they cannot reach it.

The diagnostic ROM writes a log ring at 0x81000000. The ring holds 262,144 records of 48 bytes (12 MiB). The log uses no game memory. In this build, a game patch also moves the Zelda arena to the high region.

A contract gate fails if the emulator patch, the log addresses or the arena patch change.

6.3 Capture build

The capture build applies a second source patch. The patch adds the GDB commands in Table 5.

Table 5 Capture build GDB commands

CommandResult
qDsce:coverageLists what the recorder captures.
qDsce:start, qDsce:stopStarts or stops the recording.
qDsce:snapshotWrites a full machine snapshot.
qDsce:stateGives the CPU program counter and timing state.
qDsce:test-causal-stopTests the stop function (positive control, R5).

The recorder keeps this data:

  • Each RAM write: the address, the size, the value, the CPU PC, the RSP PC and the source device.
  • The last 131,072 RSP instructions with their registers.
  • The DMA history and the RDP command batches.
  • CPU and RSP time for each code block.

The recorder can stop the emulator before the game watchdog recovers from a hang. Thus the hang state stays available for analysis.

7 Procedure: one test run

Purpose: This procedure shows how a headless test gets a result from the game and how it decides pass or fail. It tests conditions 2 and 3 of section 2.3.

Figure 2 shows one test run. The example is the ordinary mask test. Other ares tests use the same structure with a different trace record.

7.1 Run

  1. Build the test ROM. The test ROM contains the fixture.
  2. Get the trace record address from the ROM symbol map.
  3. Write the input script for the test case.
  4. Start the run tool in headless mode with the input script and the GDB server.
  5. Wait for the observation time. For the mask test, this time is 175 seconds.
  6. Read the trace record through GDB. For the mask test, the record is 48 bytes (12 words).
  7. Save the raw record to a file.
  8. Stop ares. Keep the run record.

7.2 Checks

Do the checks in the order of Table 6. The first failed check stops the test. A pass needs a result that the game itself shows (R8).

Table 6 Trace record checks (mask test)

OrderCheckExpected valueIf the check fails
1Magic numberWord 0 = 0x4D534B47The fixture did not run, the address is wrong, or the ROM is stale (R6).
2Case numberWord 1 = the requested caseThe input did not select the correct menu item.
3Bad-state flagsWord 2, bits 30 and 31 = 0The game entered a prohibited state.
4Expected eventsWord 2 contains all bits of 0x7C7FThe test gives the missing bits and the input diagnostic word.
5ValuesWords 8 to 11 (appearance data)The test gives the wrong value and the expected value.

If a check fails, go to section 10.2.

8 Procedure: movement comparison with SM64

Purpose: This procedure tests condition 1 of section 2.3. It is the main test for the Mario movement code.

The Mario movement code in the mod is the SM64 source code. Thus SM64 is the oracle for movement (R1). Figure 3 shows the procedure.

  1. A generator makes one test course. The build compiles this course into both games.
  2. Both ROMs run the same moves in a headless emulator.
  3. Each game records the Mario state for each tick: action, position, facing angle, floor height and sounds.
  4. The comparison tool converts the mod data from 20 to 30 ticks per second. Velocity uses a factor of 1.5. Acceleration uses a factor of 2.25 (R2).
  5. The tool aligns the two records at the first change of action. It does not use clock time.
  6. The tool compares the records with the relations in Table 7.

Table 7 Comparison relations

RelationRequirement
R1 Action sequenceEqual
R2 Position for each tickEqual to the bit
RF Floor heightEqual
R3 Sound familiesSame family on the same tick
CoverageAll 39 core moves occur

NOTE: The relation names R1, R2, R3 and RF are the names in the comparison tool. They are not the rule numbers of section 5.

Two runs of the same input give identical records. Thus each difference is a real difference. The tool records each known difference as a finding. It does not skip a difference.

The comparison found these faults. Both are fixed. Both checks are now equality gates.

  • Mario went to sleep after approximately 88 ticks. SM64 needs approximately 930 ticks. An animation timer advanced too fast.
  • After the frame rate conversion, Mario moved a few units through a wall. A scale step occurred after the collision check.

9 Procedure: level import checks

Purpose: This procedure tests the SM64 levels and enemies in the mod. It covers the units, memory and scale risks of Table 2.

The build makes each SM64 scene again from the pinned SM64 source. The mod changes are diff files. They are not edited copies. The castle grounds scene is the only exception. Figure 4 shows the procedure.

  1. Generate the scenes from the pinned source.
  2. Apply the mod diffs.
  3. Run the static gates in Table 8.
  4. Link the ROM.
  5. Boot all 45 areas from one build. Keep one image of each area after it settles (R9).
  6. Compare the Mario position and the camera with SM64 values (R1).
  7. The owner plays the area to answer one specific question (R10). The owner reports faults from in the game with a bug report key.
  8. If a value is different or the owner finds a fault, find the cause in the source. Write a gate that fails on the old code (R4). Fix the generator and generate the scenes again.

Table 8 Static gates for the level import

GateLimit or requirement
Unit conversionOnly lengths use the SM64-to-MM factor (1/3.432). Scales do not (R3).
Object memoryEach level bank fits in the object space.
Collision actors45 or fewer dynamic collision actors in each area. The engine limit is 50.
Sound bankFewer than 128 entries in each bank.
Animation offsetsPart offsets and animation root use the same units as the vertices.

The first area sweep (2026-09-06) took approximately eight minutes. It found these faults:

  • Six areas did not load. A shared sky data pack was too large.
  • Static objects in 18 areas had no draw function.
  • The arrival camera was incorrect in approximately twelve areas. Two arguments of a pitch function were in the wrong order.
  • Shifting Sand Land crashed on arrival. Seven animation functions read data with a graphics segment address that the CPU cannot use.

10 Fault diagnosis

Purpose: This section gives the procedures to find the cause of a failed test. Use it after any layer in section 3 finds a fault.

10.1 Select the procedure

Table 9 Symptoms and procedures

SymptomProcedureEmulator build
A trace record check fails (Table 6)10.2Stock, then 32 MiB or capture
The image stops. The frame counter does not change.10.3Capture
Some frames are slow10.4Stock
The fault screen shows10.5Stock

Reproduce each fault in ares first. Do not use Mupen for this step. The Mupen graphics plugin ignores some bad display list commands. A real N64 and ares stop on these commands. For example, a freeze with the Blast Mask did not occur in Mupen after many hours of tests. It occurred in ares on the first attempt.

All procedures end with the same steps:

  1. Write down the cause.
  2. Write a gate for the fault. Make sure that the gate fails on the code before the fix (R4).
  3. Do the fix. Run the gate again.

10.2 RAM values are not as expected

Figure 5 shows this procedure. Steps 1 to 4 find faults in the test itself. Do these steps before you examine the game code.

  1. Compare the ROM time with the source time. If the ROM is older, rebuild it and run the test again (R6).
  2. Make sure that the inputs reached the game. Use a value in the game, for example the inventory or the player state (R8). Hold each press for 30 frames or more.
  3. Do the same measurement on a known good build (R5). If the result is the same, the measurement is wrong. Correct the measurement.
  4. Do a positive control. Make sure that the instrument detects a known event. If it does not, correct the instrument.
  5. Read the log ring from the 32 MiB build.
  6. Set a write watchpoint on the full RAM range of the wrong value. Do not watch only part of the range.
  7. If the watchpoint stops the CPU, read the PC. The PC identifies the code that wrote the value.
  8. If the watchpoint does not stop, the CPU did not write the value. Use the capture build to record all RAM writes. The record identifies the RSP, RDP or DMA source.
  9. Do the end steps in 10.1.

CAUTION: Do not write buttons directly into game RAM through GDB. The emulated data cache keeps the CPU copy, so the game does not see the write. Use the input bridge.

CAUTION: After a breakpoint stop, remove the breakpoint, step one instruction, and set the breakpoint again. If you do not, the emulator stops at the same breakpoint again.

CAUTION: Read all GDB replies after each stop. If you do not, the memory reads move by one block. Compare the boot code in a RAM dump with the ELF file to validate the dump.

10.3 Freeze

Figure 6 shows procedures 10.3 to 10.5.

  1. Make sure that the game frame counter does not change and that the graphics thread waits on its queue.
  2. Use the capture build to stop the emulator before the watchdog.
  3. Dump the full RDRAM.
  4. Follow the current graphics task from the scheduler one command at a time. The first bad command identifies the display list and its caller.
  5. Do the end steps in 10.1.

10.4 Slow frames

  1. Run the frame spike capture tool with the ROM, the save and the input script.
  2. For each slow frame, the tool writes a full 8 MiB RDRAM dump, the CPU registers, the timing history, the inputs, the symbol map and a manifest.
  3. Compare the timing history to find the slow code.
  4. Do the end steps in 10.1.

A timing number without the dump is not sufficient evidence.

10.5 Crash

  1. Read the fault record: the faulted thread, the PC and the bad address.
  2. Find the PC in the symbol map.
  3. Find the bad address in the symbol map. The address often identifies the data that the code tried to read.
  4. Do the end steps in 10.1.

12 Limits

Purpose: This section gives the limits of the test system.

  • Emulator results do not replace a test on a real N64 (EverDrive).
  • The 32 MiB build and the capture build are for diagnosis only. They are not release controls.
  • Section 7 uses the mask test as its example. Other tests read different trace records and check different values.
  • Some quick headless image captures use Mupen. Mupen results do not prove that the game does not freeze.
