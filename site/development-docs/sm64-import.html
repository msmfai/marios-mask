Mario's Mask builder

SM64 import pipeline

Purpose: describe how imported content is made by generators, not by hand, and how it is proven correct.

Summary

The SM64 levels and actors are not copied by hand. Generators make them from the player's own SM64 data on each build. Project changes are stored as a list of small, checked edits to that data. Thus an agent never edits imported content directly, and each change can be repeated and reviewed.

The original SM64 game is the reference for correct behavior. Tests run it next to the mod and compare the results (see document 7).

Procedure

  1. The build makes an inventory of the player's SM64 data and stores it as a fixed snapshot. The project never edits the snapshot.
  2. Project changes are ordered edit operations, each with a stable ID. An edit that replaces or removes a record must give the digest of the record that it expects. If the source changed, the edit fails.
  3. The build applies the edits to the snapshot. The result is the composed world.
  4. Generators make scenes and collision from the composed world.
  5. The build lists the actors and stages them into the ROM.
  6. Tests compare the mod with the original SM64, and an area sweep loads each area.
  7. A gate accepts or refuses each behavior. A fault is fixed as a new edit, not in generated output.

The one exception

The castle grounds outside Peach's castle are written by hand. The owner wants direct control there. All other content must regenerate from the source on each build.

Conversion terms

SM64 and MM use different units, rates and scales. Each term needs its own check. An error in one term does not show in a check of another term.

Checks

  • The movement comparison runs the real SM64 ROM headless next to the mod and compares Mario tick by tick. Action chains and position steps match bit for bit. Sound families match in all 12 scenarios.
  • The area sweep loads and photographs all 45 SM64 areas from one build in about 8 minutes.
  • A behavior reaches the shipping build through a promotion chain. The chain updates the production count, the expected set, a guard for that behavior and the catalogue digests.

Rules

  • Gates are written by people and agents, and they can be wrong. When a gate refuses a change, first prove what the source does. Then correct the gate table and record the values before and after.
  • To learn what an area ships, run the stager. Do not read its inputs. One agent read one input and reported "0 of 23 objects". The stager shipped 21 of 23.
  • Content mixes both ways: an SM64 enemy can appear in an MM level, and an MM enemy in an SM64 level. MM scene collision stays the authority. Fast SM64 collision paths keep an MM fallback.
