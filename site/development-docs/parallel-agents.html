Parallel agents and integration

Purpose: tell when to run more than one agent, and give the controls that make parallel work safe.

Summary

The default is one agent that writes code. More agents were added only for work that splits into independent parts. When several agents ran at once, each agent had its own branch, worktree and merge request. One manager agent combined the results.

Parallel work was not faster by default. Agents that shared an emulator, a branch or build products interfered with each other.

When to use parallel agents

An internal review of the July 2026 Codex sessions found about 19 owner requests for parallel work, in 13 sessions. Shared emulator state, shared branches, shared build products and long debugging chains caused interference. The review recommends one writable agent by default. Add an agent only if all these conditions are true:

  1. The work splits into parts that share no changeable state.
  2. Each part has its own acceptance test.
  3. One coordinator owns the combined result.
  4. The cost to merge is less than the time saved.

The review also cites an outside study in which multi-agent coding setups did 1.3% to 12.8% worse than a single agent.

Isolation

  • Each task is a GitLab work item with one feature branch, one worktree and one merge request.
  • The owner describes the task in a staging file. The tooling does nothing until the owner changes the file from "draft" to "ready". Then it creates the item, branch, worktree and agent session.
  • The worker's first prompt names its branch and worktree. It forbids branch switching, writes to other worktrees, force pushes, merges and rebases.
  • GitLab is the durable record: work items, merge requests, labels, notes, pipelines and exact commit SHAs. Terminal messages between agents are only a convenience.
  • All agents share one computer. An agent stops only the processes that it started. It never stops a program by name.

Procedure

If the manager rejects a handoff, the worker continues on its branch and hands off again.

Roles

RoleCanCannot
OwnerApprove tasks, make design decisions, confirm fixes
Manager agentReview, merge, close items, retire worktrees, change any merge request stateMerge a SHA that it did not review and accept
Worker agentEdit, commit and push its own branch; change the state of its own merge requestMerge, rebase, force push, switch branch, write to other worktrees

Handoff types

  • Integration handoff. The worker says that its exact pushed SHA is ready to merge. The manager reviews that SHA.
  • Diagnosis handoff. The worker reports a cause but no fix. This is not approval to implement or merge a fix. The owner decides what happens next.

The integration found faults that the tests on each branch did not find:

  • Two workers used the same dialogue message ID. Each branch passed its own tests. The fault showed only after the merge, and the manager fixed it.
  • A merge conflict in a test file had to keep 8 newer checks from one branch and 15 new checks from another. The manager combined them by hand.

Thus integration is work, not a formality. Plan time for it.

Limits of this record

  • The review planned a direct comparison of one agent and several agents on this project. No result was found.
  • The review covers the Codex sessions only.
