Verification loop and evals

Purpose: describe how agent output was checked, so that a result is accepted for evidence and not for the agent's report.

Summary

An agent reports success with the same confidence whether it is right or wrong. Thus no agent report counts as evidence. A change is accepted only when the game itself shows the correct result, measured against a reference that the agent did not write.

For Mario's Mask, the reference is the original Super Mario 64 game. Mario's movement code in the mod is the SM64 source. Thus the correct answer for each movement is the value that SM64 itself produces with the same input.

The loop

  1. The agent changes the code.
  2. Static gates check the source and data on each build: unit conversions, memory budgets, engine limits.
  3. Emulator evals run the ROM headless with recorded inputs and read the results from game memory.
  4. If an eval fails, the agent finds the cause. It writes a gate for that fault and proves that the gate fails on the old code. Then it fixes the cause and runs the loop again.
  5. If all evals pass, the owner plays the build. Each fault that the owner reports enters the same loop.
  6. Before a release, the build runs on a real Nintendo 64.

Each fault leaves a gate behind. Thus the eval suite grows from real faults, not from a plan written in advance.

Oracle comparison

One test course is compiled into both games. Both ROMs run the same inputs. Each records Mario's action, position, facing, floor height and sounds on each tick. A tool converts the mod's 20 updates per second to SM64's 30, aligns the two records at the first change of action, and compares them.

  • The requirement is equality: the same action sequence and the same position to the bit.
  • Two runs of the same input give identical records. Thus each difference is a real difference. Known differences are recorded as findings, not skipped.
  • Result: 54 actions equal to the bit, 0 failures. The comparison found faults that play did not, for example Mario fell asleep after 88 ticks instead of about 930.

In-game fixtures

The test reads a fixed record that test code in the ROM writes. The checks run in order, and the first failure stops the test:

  1. A magic number. If it is wrong, the fixture did not run or the ROM is stale.
  2. The case number. If it is wrong, the input did not reach the game.
  3. Flags for prohibited states.
  4. Flags for the expected events.
  5. The measured values.

The first two checks test the test. Many apparent faults were in the test setup, not in the game.

Area sweep

One build loads every imported area and keeps one image of each. The first sweep took about 8 minutes and found 4 fault classes that manual play had not found, one of them in 18 areas.

Owner reports as eval cases

The owner plays with a capture button. Each report holds a screenshot, a save state, the build identity and the game context decoded from RAM. A freeze is filed automatically with a full RAM dump. The agent loads the state and sees the fault itself. An agent can mark a report fixed, but only the owner marks it verified.

Rules for honest evals

Each rule comes from a wrong result on this project.

RuleWrong result that produced it
Use the original game as the oracle, not a description of it.Descriptions gave values that the game does not produce.
Accept only results that the game shows.Input playback succeeded on the host while the game received nothing.
A new gate must fail on the code before the fix.A gate passed the exact fault it was written for, because the generator split one command over two lines.
Run every measurement on a healthy build first, and prove the instrument detects a known fault.Several freeze "causes" gave the same value on a good build.
Never measure a ROM older than its source.A capture reported the previous build.
Check relations, not fixed numbers. Check every term of a conversion.A model had the correct scale, but its parts were 3.4 times too far apart. The same fault was in 26 actors.
Look at the image.A size ratio cannot tell a small model from a model in pieces.
When a gate rejects correct code, examine the gate.A budget gate counted one spawner's children for each actor and reported 58 of 45. The real count was 27.
Reproduce in the emulator that shows the fault.One freeze never occurred in one emulator after hours of tests. It occurred on the first try in another, and on hardware.

Cost control

  • During development, run only the focused suites for the changed path.
  • Exhaustive checks, such as loading every scene from every entrance, run only before a release.
  • Long runs go to a background process. The agent continues other work while they run.
  • Emulator results never replace the real N64 test.
