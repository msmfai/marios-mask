Mario's Mask builder

Release and distribution

Purpose: describe the release process and the reason for each gate.

Summary

Mario's Mask is made from three Nintendo games. The project cannot distribute their data. Thus players get a builder and a recipe. The builder reads the player's own three ROMs and builds the mod on the player's device.

The release process proves two things: the public files contain no Nintendo data, and the published builder makes exactly the tested ROM.

The recipe

The recipe is a list of operations that write the output ROM. There are five operations:

  1. Copy bytes from Majora's Mask.
  2. Copy bytes from Super Mario 64.
  3. Copy bytes from data derived from Ocarina of Time.
  4. Write bytes stored in the recipe (the project's own code and data).
  5. Copy bytes already written to the output.

The builder refuses a wrong input or output digest, a copy outside the input, and extra data at the end of the recipe.

Public boundary audit

The audit reads every file in the whole public history, not only the current files. It refuses:

  • ROM, save, archive, audio and image file types, except reviewed images pinned by SHA-256;
  • top-level folders for source, assets, builds and extracted data;
  • data that starts with an N64 ROM header;
  • compressed payloads, binary data and text that is not UTF-8;
  • a recipe larger than 8 MiB.

Release stages

  1. Check that the private release worktree is clean and that the inputs are the accepted ROMs.
  2. Run the release suites: static, gameplay, memory, fusion, bottles and minigames.
  3. Refuse the release if any memory case runs out of memory or reaches a critical limit.
  4. Build the release ROM and record its hashes. This file is the reference for all later checks.
  5. Generate the public recipe and the version numbers.
  6. Audit the public files. Build the builder and make sure that it makes the reference ROM byte for byte. Make sure that it fails when any one of the three ROMs is missing.
  7. Update the private release branch, so that everything published is also in the private record.
  8. Merge the release into the public main branch through a pull request.
  9. Push the tag. The public build system makes the packages.
  10. Download the package for the current platform, audit it and rebuild the ROM with it.
  11. Check that the public web page serves the same web builder as the release.

The tool saves a checkpoint after each stage. After a failure, fix the cause and run the same command again. It skips the stages that are still valid.

  • A stable tag never changes. If a stable release has a fault, the fix is a new version.
  • Builders exist for Android, Linux, Windows, Apple Silicon macOS, Intel macOS and the web.
  • The public web page always serves the stable builder.
  • Releases run only when the owner asks for them.

Limits

Each stable release passes the emulator gates. The real-console gate is still open.
