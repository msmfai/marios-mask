Performance and memory

Purpose: give the procedure for slow frames and out-of-memory faults, and the rule that a control comes first.

Summary

The N64 has little RAM and a slow CPU. Majora's Mask already uses most of both. Mario's code, models and sounds must fit in what is left. Two faults result: the game runs out of memory in a scene, or a frame takes too long.

Agents often reported a confident cause for these faults that a control later disproved. Thus every measurement in this document starts on a healthy build.

Constraints

  • The base N64 has 4 MiB of RAM. Majora's Mask needs the 8 MiB Expansion Pak. The real-hardware test uses it.
  • Each scene's actors and objects come from one memory area, the Zelda arena. The game destroys this arena at each scene exit and makes a new one.
  • ROM space is large and RAM is small. Data that the game does not change stays in ROM. The game loads only the data that the current scene, actor or form needs.

Procedure

  1. Build a release control: the same game without the change under test.
  2. Run the measurement on the control. Make sure that it detects a known fault (positive control). If it does not, fix the instrument first.
  3. Run the same measurement on the branch.
  4. If both numbers are the same, the change is not the cause. Report both numbers.
  5. If the numbers differ, walk the memory arenas on both builds and find the allocation that differs.
  6. Fix the fault where the data lifetime starts or ends, for example at a scene change.
  7. Measure both builds again.

Frame-spike capture

A report of a slow frame needs the game state at that frame. A timing-only probe is not sufficient evidence. The capture tool runs the ROM headless in ares with recorded inputs:

  • It compares each frame time with a rolling median. A spike is 20 ms over the median, or 1.5 times the median. The larger limit applies.
  • For each spike, it saves the files in the table below.
  • It removes its own save time from the next frame time, so that a capture does not cause a new spike.
FileContent
RAM imageAll 8 MiB of RDRAM
CPU registersThe state of the CPU at the spike
ManifestFrame number, frame time, median, ROM hash, decoded game state, timing history
Symbol mapAddresses of the ROM symbols, to read the RAM image
Input scriptThe inputs that produced the spike

Area memory census

The census loads each scene in every way that the game can enter it, and records free memory. Unmodified Majora's Mask is the reference.

  • It tests all 454 entrance and spawn pairs at day 1 noon, and 102 scenes at 9 day and time states (918 cases).
  • Each case uses a new emulator.
  • It is a release gate. It takes a long time, so it is not run during ordinary development.

Rules

  • Run every measurement on a healthy build first. Report both numbers.
  • A measurement tool must detect a known fault before its result counts.
  • Use ares for hangs. Some emulators skip bad graphics commands, so a hang does not occur there. One freeze survived hours of tests in another emulator and occurred on the first try in ares.
  • The census starts as Link, not as Mario. Thus it does not show Mario's worst case. Do not report Mario memory savings from it.
  • Loading on demand does not lower the peak while Mario is active. It lowers memory use in scenes where Mario is not present.
